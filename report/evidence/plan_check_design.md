- 확정: 2026-11-09 Day 5 저녁, **구현·더미 작성 전**에 고정. 결과를 본 뒤 이 문서의 기준을 바꾸지 않는다
- 근거: project_plan.md 15판 9항, 가이드 106줄(심화는 정량 비교 필수)

## 0. 대상

- 더미 기획서 3개(A·B·C) × **AI 사용 항목 3개 = 9개**
- 기획서마다 AI를 쓰지 않는 함정 항목 1~2개 (잘못 찾는지 확인용)
- 더미 기획서·정답표는 `eval/`에만 둔다. 지식베이스에 저장·임베딩하지 않는다
- 평가셋(P·F·C·U·G·S)과 확인 질문(Y·Z·W·N·V)의 업종·AI 부분·공개 여부 조합과 겹치지 않게 만든다

## 1. 처리 흐름 (측정 대상)

```
기획서 전체 → [LLM] AI 사용 항목 추출: 항목마다 ① 원문 인용(글자 그대로) ② 혼자 읽히는 질문 한 줄
                       (업종·시기·공개 방침처럼 기획서 다른 곳에 적힌 정보를 질문에 담음 = 질의 재작성)
           → [LLM] features.extract(질문)  ※ exp9 프롬프트 그대로, 새로 고치지 않음
           → [코드] reaction.predict → 검색 → 답변 (2-1 ⑦~⑩과 같은 경로)
```

- LLM이 들어가는 단계는 **3회 실행**, 평균과 실행별 값을 함께 기록

## 2. 정답표 형식 (`eval/plan_gold.jsonl`, 항목마다 한 줄)

| 키 | 내용 |
|---|---|
| `plan_id`, `item_id` | 예: `A`, `A1` |
| `is_ai` | AI 사용 항목이면 true, 함정 항목이면 false |
| `sentence` | 기획서 원문에서 그 항목을 설명하는 1~2문장 (글자 그대로) |
| `anchor` | 그 항목에만 있는 짧은 원문 구절 (기획서 안에서 한 번만 나와야 함) |
| `features` | 특징 4개. 기획서에 없는 특징은 null |
| `gold_case_ids`, `gold_grade` | 정답 특징을 `reaction.predict()`에 넣은 결과 (스크립트로 계산해 **구현 전에** 파일에 박음) |

## 3. 지표와 판정 (모두 코드 판정)

| 지표 | 계산 | 함께 기록 |
|---|---|---|
| ① 항목 추출 재현율 | 찾은 AI 항목 수 / 9. 추출 인용이 원문에 그대로 있고(공백만 정리) 정답 `anchor`를 포함하면 찾은 것. 추출 하나는 정답 하나에만 대응 | 잘못 찾은 항목 수 (함정 항목 포함, 어느 정답에도 안 맞는 추출) |
| ② 특징 추출 정확도 | ①에서 찾은 항목만. 칸 단위(항목 × 4) 정답률 + 항목 단위 "4개 모두 맞음". 정답이 null이면 null이 정답 | 등급 일치, 비슷한 사례 목록 일치 (참고) |
| ③ 사례 검색 Hit@3 | 아래 A·B. 정답 사례가 0개인 항목은 빼고, 뺀 수를 기록 | MRR, 문항별 표 |

**③ A와 B** (검색어는 둘 다 정답표의 `sentence`로 고정 → 바뀌는 변수는 "검색 범위" 하나)

| | A: 그대로 검색 | B: 특징 추출 후 검색 |
|---|---|---|
| 검색 범위 | 탈락 사례만 제외 (정부·뉴스 포함, `retrieve()`의 비슷한 사례 0개일 때와 같음) | ②의 추출 특징 → `predict()`의 비슷한 사례 안에서만. 0개면 A와 같은 범위 |
| 실행 | 1회 (LLM 없음) | 3회 (실행마다 추출 특징이 다름) |
| 항목을 못 찾은 경우 | 해당 없음 | 그 실행에서 그 항목은 **0점** (실제로 예상이 나오지 않으므로). 건수 따로 기록 |

- 맞음 = 위 3개 중 `case_id`가 `gold_case_ids`에 있는 청크가 하나라도 있음 (`run_eval.is_hit`과 같은 기준)
- **참고값** (결론에 쓰지 않음): 기획서 전체를 한 번 검색한 위 3개로 그 기획서의 각 항목을 채점. 1회

## 4. 결론 기준 (결과 전 고정)

- "B가 낫다"는 **3회 모두 B의 Hit@3 > A**일 때만. 반대도 같음. 그 밖은 "차이 없음"
- 항목 9개라 1개 차이(약 11%p)는 흔들림일 수 있음 → 수치와 문항별 표를 함께 제시
- B 점수는 범위를 좁혀 부풀려지는 구조 → "B의 Hit@3 ≈ 특징 추출이 맞았는가"를 리포트에 함께 적음
- ①②에는 목표치를 두지 않는다 (기준이 될 이전 값이 없음). 수치와 실패 항목을 그대로 기록

## 5. 오염 방지

- 정답표는 구현 전에 확정하고 커밋. 이후 수정하지 않음 (오기 발견 시 고친 이유를 따로 기록)
- 더미 결과를 보고 추출 프롬프트·features.py를 고치지 않음. 실패는 남은 한계로 기록
- 항목 추출 프롬프트에 예시를 넣으면 더미와 다른 업종·AI 부분 값으로

## 7. 개선 실험 exp_plan_common (2026-11-09 추가, deep_plan 결과를 본 뒤·개선 전 측정 전에 고정)

- 계기: deep_plan(A·B·C)에서 LLM이 다시 쓴 질문이 표기 방침·시기를 빠뜨림 (공개 0/9) → B가 범위를 한 번도 좁히지 못함
- 바꾸는 변수 하나: 질문 만드는 방식. LLM은 원문 인용만(항목 + 공통 정보 회사·AI 표기 방침·시기), 질문은 코드가 조립. 원문에 없는 공통 인용은 코드가 버림
- 평가 오염 방지: A·B·C는 결과를 보고 고쳤으므로 판정에 쓰지 않음. 새 더미 D·E·F(`eval/plan_gold2.jsonl`)를 먼저 만들고, **지금 코드로 기준선**(deep_plan2_before)을 잰 뒤 코드 변경
- 새 더미 조건: 업종·조합이 평가셋·확인 질문·A·B·C와 겹치지 않음. 공통 정보 적는 방식을 바꿈(표, 맨 끝 유의사항, 분기 표기)
- 채택 기준 (D·E·F): ② 칸 정답률 3회 평균이 개선 전보다 높고, ① 재현율 3회 평균이 1항목(0.11) 넘게 떨어지지 않음
- ③ B vs A 결론 기준은 4항 그대로
- 새 더미 결과를 보고 다시 고치지 않음
- 한계: 바꾼 방식은 A·B·C 실패를 보고 떠올린 것. 효과 판단은 D·E·F로만
