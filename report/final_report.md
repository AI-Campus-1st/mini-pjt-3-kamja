# [최종 리포트] 생성형 AI 활용 광고 소비자 반응 예상 RAG 챗봇
### 미니프로젝트 3 — 공공 문서·웹검색 결합 RAG 기반 질의응답 시스템
작업 기간: 2026-11-03(화) ~ 2026-11-10(화)

---

## 개요

> **AI 이미지를 쓰려는 신입 마케터·기획자**에게, 국내 AI 광고 사례의 유튜브 댓글 반응을 근거로  
> "어떤 반응이 나왔는지"를 알려주고 기획서를 검토해주는 챗봇.

| 구분 | 핵심 수치 |
|---|---|
| 지식베이스 | 유튜브 댓글 5,457 → 정제 2,290개(사례 11개, 자격 7개) · 제공 뉴스 16건 · 정부 안내서 2종(191쪽) → 청크 564개 (KURE-v1) |
| 분류 신뢰도 | 사람 검수 새 40개 기준 방향 57.5% · 묶은 이유 67.5% · 부정 여부 85.0% |
| 검색 (32문항) | Hit@1 · Hit@3 · MRR = 0.719 · 0.781 · 0.770 → **0.812 · 0.875 · 0.846** |
| 답변 (32문항) | 정확 14 → **16** (43.8% → 50.0%), 오답 7 → **4**, 정확+부분 78.1% → 87.5% |
| 거절 (8문항) | 8/8 거절, 잘못 거절 0 |
| 실패 원인 | 정확이 아닌 16문항 = ③ 답변 12 + ④-추출 4. **코드 규칙(④-규칙)이 원인인 문항 0** |
| 심화 | 기획서 확인: 칸 정답률 0.333 → **0.893** (새 더미로 판정, 3회 평균) |

**작동 방식**  
1. 코드가 수치를 먼저 박으면 LLM이 따르도록 하고 질문 조립을 코드로 옮기니 정답률이 올랐다.
2. LLM은 '한계 안내, 시기 변환, 무엇이 제작 항목인가' 등 판단하는 문장을 맡는다.
    

## 1. 시스템 정의

### 1-1. 사용자

| 항목 | 내용 |
|---|---|
| 누구 | 광고·SNS 콘텐츠·팝업을 기획하는 신입 마케터·기획자 |
| 언제 | 기획 단계에서 AI 생성 이미지(모델 인물, 제품 이미지, 영상 전체 등)를 쓸지 검토할 때 |
| 알고 싶은 것 | ① 어느 부분에 AI를 쓰면 소비자가 어떻게 반응하나 ② 그 근거는 무엇인가(사례·비율·댓글) ③ 권리 측면에서 정부 기준에 걸리는 것이 있는지 |

**설계 원칙 3가지**
1. **비슷한 과거 사례에서 실제로 관찰된 반응 패턴**을 찾아 예측하는 도구다.
2. 반응 예상 등급과 비율은 **코드 규칙**이 정한다. LLM은 계산된 결과를 문장으로 옮기거나 대표 댓글을 고르기만 한다.
3. 개별 사안의 합법·위법은 판단하지 않는다.

### 1-3. 답변 불가 유형
아래와 같은 경우, `rag/scope.py`를 통해 답변 불가 유형 (7유형)으로 판정한다.
- 유사 사례 2개 미만
- 지식베이스에 없는 성과 수치 (예. 매출 %)
- 개별 법률 판단
- 표시 의무 규정 (수집 밤위 밖)
- 해외 사례
- 유튜브 외 SNS 반응

개별 법률 판단만 **약한 거절**(판단 거절 문구 + 일반 기준 안내)로 처리하고, 판정을 놓치면 답변 단계의 "제공된 자료에서 확인할 수 없습니다"가 2차 방어를 한다.

### 2-4. 직접 수집 대상의 선정 근거와 소스 탐색 과정

- **유튜브 댓글**
     - 잠재고객의 직접적인 반응을 얻을 수 있는 SNS 매체 중 하나고, 그중 공개 API로 사례별 반응을 모을 수 있으며 댓글 작성자 정보를 빼고 저장하는 데 용이하다.
     - AI 논란으로 광고를 닫은 경우에도 뉴스 리포트 영상으로 남는 경우가 많았기에 광고가 사라진 사례도 댓글을 쉽게 얻을 수 있었다.
     
- **사례 선정 기준**
     - AI로 만든 광고 이미지·영상일 것(AI 서비스를 광고한 실사 영상 제외)
     - 원기사나 영상 속 AI 표기로 사실 확인 가능
     - 댓글이 열려 있고 이벤트성 댓글이 대부분이 아닐 것
     - 국내 사례.

- **후보에 있었으나 제외된 사례**
     - 범위 밖 : 뤼튼×지드래곤, 스픽, 와플대학, 선관위 영상
     - 근거 부족 : 정식품, 슬릭, 더페이스샵, 에듀윌
     - 댓글 품질 : LG유플러스 이벤트성 댓글, 롯데웰푸드 댓글 이벤트

- **수집 조건**
     - 인기순(`order=relevance`, API 기본값은 최신순이라 코드에서 명시)
     - 최상위 댓글 영상당 500개(시프트업만 2,000개)
     - 수집된 댓글의 답글 전부 포함(`comments.list` + `parentId`).


### 2-5. 커버리지 한계 (요약, 자세한 내용은 9항)

- 반응은 유튜브 댓글만, 국내 사례만 다룬다.
- 자격 사례 7개라 대부분 조합이 "근거 부족"이다.
- 사례 11개 중 10개가 AI 사용을 공개해 공개 여부에 따른 차이는 검증할 수 없다.
- 제공 뉴스에 AI 이미지 광고 기사가 없고, AI 생성물 표시 의무 규정은 수집 범위 밖이다.



## 3. 파이프라인 설계

### 3-1. 계층 구조 (단방향)

```
[collector]  유튜브 댓글 수집(작성자 정보 제외) · 제공 뉴스 16건 적재 · 정부 PDF 적재 · 사례 카드
     │ 원문 저장 (store/docs.db)
     ▼
[indexer]    파싱 · 정제 · 중복 제거 · 댓글 분류(GPT 배치) · 사례 요약(코드 계산) · 청킹 · 임베딩
     │ 적재 (store/chroma, 컬렉션 kb_kure_v1)
     ▼
[store]      chroma/ (청크 564 + 메타데이터) · docs.db (원문·분류 결과·청크)
     ▲ 조회만
[rag/]       retriever · features · reaction(등급 규칙) · scope · compare · rewrite · filters · chain
     ▲                                   ▲
[app/] Streamlit 챗봇·기획서 확인·대시보드   [eval/] 평가 하네스 (같은 rag/chain.py 호출)
```

- 챗봇은 **질문 임베딩만** 만든다. 문서 임베딩·인덱스 쓰기는 indexer에서만 한다. 화면용 메타 추가(`display_name`, `year`)도 indexer 스크립트로 따로 했다.
- **구조 검사** (`eval/check_layers.py` → `report/evidence/check_layers.md`)
     - indexer·collector를 막은 상태에서 챗봇 모듈 5개 불러오기 성공
     - 실제 답변 1회 전후 인덱스 건수 같음, app 2개·eval 7개가 같은 `rag/chain.py`를 import
     - 벡터 DB 메타 키 27개에 작성자 정보 없음
     - `.env` 미추적·키 문자열 없음
     - **통과가 아닌 항목 0** (질문 임베딩 2곳은 "허용")

### 3-2. 청크 메타데이터와 선정 이유

| 필드 | 대상 | 선정 이유 |
|---|---|---|
| `doc_id`, `title`, `source`, `url`, `published_at`, `collected_at` | 전체 | 가이드 출처 표시 요건. 화면 출처 목록(종류·제목·발행처·발행일·링크) |
| `doc_type`, `authority` (소비자 반응 / 언론 보도 / 정부 기준) | 전체 | 출처 종류 표시, 문서 종류 필터, 종합 질문에서 종류별로 나눠 찾기(exp10) |
| `case_id`, `industry`, `ai_part`, `disclosed`, `period` | 댓글·사례 요약 | 비슷한 사례 판정(특징 일치)과 검색 범위 좁히기, 업종 필터 |
| `qualified` | 댓글·사례 요약 | 표본이 부족한 사례를 예상 근거에서 빼기 |
| `direction`, `reason`, `n_comments` | 댓글 | 대표 댓글 고르기, 근거 표의 댓글 수 |
| `video_kind` | 댓글 | 공식 영상과 뉴스 영상의 반응 차이 해석 |
| `section`, `page_start`, `page_end` | 정부 문서 | 쪽 번호 인용, 정책 문항 쪽 단위 채점 |
| `scheme`, `chunk_index`, `chunk_id` | 전체 | 청킹 2안 비교(같은 저장소에서 안별로 거름) |
| `run_tag` | 사례 요약 | 어떤 분류 결과로 만든 요약인지 추적 |
| `year`, `display_name` | 전체 / 사례 요약 | 기간 필터(Chroma는 숫자만 크기 비교), 화면 사례명 |

- 값이 없는 필드는 키를 넣지 않는다(빈 특징값은 어떤 값과도 일치하지 않음).
- 작성자 이름·채널 ID·프로필은 저장하지 않는다. 답글의 `@닉네임`은 저장 전에 `@사용자`로 바꾼다.

|---|---|---|

챗봇이 **근거 없이 그럴듯한 예상을 내는 것**을 제일 큰 위험요소로 봤기 때문이다. 사례 2개 미만 조합, 매출 수치, 법률 판단, 표시 의무, 해외 사례처럼 지식베이스가 답할 수 없는 질문을 8문항(20%) 넣어 거절 정확도와 잘못 거절을 함께 쟀다. 답변 불가 문항은 Hit 계산에서 빼고(Hit 대상 32문항) 거절로만 채점했다.

## 8. 실패 사례 분석

### 8-1. 원인 층 분류 방법

- 원인 층은 폴더 계층(collector → indexer → store → app)이 아니라 **답이 만들어지는 기능 단계**다.

- ④는 성격이 다른 두 단계로 나눴다.
     - **④-추출** :  LLM이 질문·기획서에서 특징·의도·항목을 뽑는 단계(`rag/features.py`, `rag/plan_check.py`)

     ① 분류 오차는 문항 하나의 실패가 아니라 모든 비율에 섞인 오차로 따로 적는다.

### 8-4. 정리

1. 정확이 아닌 16문항은 모두 LLM 단계에서 생겼고, 코드 규칙이 원인인 문항은 없었다.
2. 코드가 수치를 먼저 붙이면(exp13) LLM이 따르고, 질문 조립을 코드로 옮기면(심화) 칸 정답률이 0.33 → 0.89로 오른다. **같은 처방이 두 기능에서 통했다.**
3. 그래도 LLM이 혼자 판단하는 부분(한계 안내, 원문의 단정 정도, 시기 변환, 무엇이 제작 항목인가)은 남는다. 실제 업무에서 사람이 확인해야 한다.
4. 규칙의 한계는 계산 오류가 아니라 특징 설계의 한계다.

     - 정확이 아닌 16문항 모두 LLM 단계에서 나왔다.

### 9-4. 실제 업무에 적용하려면 추가로 필요한 것

1. **사례와 반응 채널을 늘린다**  
     특히 공개 여부가 다른 사례(AI 사용을 나중에 밝힌 사례)가 필요하다. 커뮤니티·매장 설문을 더하면 댓글 작성자 편향을 줄일 수 있다.

2. **분류를 사람이 더 검수하거나 이유 코드를 다시 설계한다**  
     방향 일치 57.5%로는 비율 차이를 강하게 말하기 어렵다.

3. **LLM이 혼자 쓰는 문장을 코드로 옮긴다**  
     다음 후보: `exp17_synth_head`(종합 질문 수치 줄), `exp15_compare_fallback`, `exp16_scope_numbers`, `exp14_reason_label`, `exp8_notoc`.  
     각각 변수 하나만 바꾸고 평가셋 밖 질문으로 함께 확인한다.

4. **원문 대비 단정 정도를 검사한다**
     S01처럼 번호는 맞고 서술이 부풀려진 경우는 현재 검사로 잡히지 않는다. 정부 문서 인용 문장은 원문 인용으로 보여 주는 방식이 필요하다.

5. **운영 규칙을 정한다**  
     YouTube 30일 재수집 주기, 올린 기획서의 외부 전송 고지, 범위 밖 법·제도 질문을 사람에게 넘기는 절차.

6. **예상 결과는 기획자 판단을 돕는 참고 자료로만 쓴다.**  
     최종 판단과 문구 결정은 사람이 한다.



## 10. 심화 확장 결과: 기획서 확인 기능

### 10-1. 동작

```
기획서(붙여 넣기 또는 PDF·Word·HWPX) → [LLM] 원문 인용만: AI 사용 항목 + 공통 정보(회사·AI 표기 방침·시기)

  → [코드] 원문에 없는 인용 버림, 항목마다 질문 조립 → [LLM] 특징 추출 (exp9 그대로)
  → [코드] 비슷한 사례·등급 → 항목 카드
  → (관찰됨일 때만) [LLM] 가상 소비자 한마디 + 이유 → [코드] 근거 번호·숫자·등급 단어 검사
```


### 10-2. 측정 설계 (결과 전 고정, `report/evidence/plan_check_design.md`)

| 지표 | 내용 |
|---|---|
| ① 항목 추출 재현율 | 정답표 AI 항목 중 찾아낸 비율 (함정 항목을 잘못 찾은 수 함께) |
| ② 칸 정답률 | 찾은 항목의 특징 4칸이 정답표와 맞는 비율 |
| ③ 사례 검색 Hit@3 | [A: 기획서 항목 문장 그대로 검색] vs [B: 특징으로 범위를 좁힌 검색] / "B가 낫다"는 3회 모두 B > A일 때만 |

더미 기획서 6개(A·B·C 첫 측정, D·E·F 개선 판정 전용), 기획서마다 AI 항목 3개 + 함정 1~2개, 3회 반복(gpt-4.1-mini, temperature 0).

### 10-3. 정량 결과

| 지표 | A·B·C 첫 측정 | D·E·F 개선 전 | **D·E·F 개선 후** |
|---|---|---|---|
| ① 재현율 / 잘못 찾음 | 0.963 / 0 | 0.889 / 0 | **0.778 / 0** |
| ② 칸 정답률 / 4칸 모두 | 0.471 / 0.0 | 0.333 / 0.0 | **0.893 / 0.571** |
| 등급 일치 (참고) | 0.537 | 0.625 | **0.857** |
| ③ A Hit@3 vs B Hit@3 | 0.429 vs 0.429 | 0.5 vs 0.5 | **0.5 vs 0.667 / 0.5 / 0.667** |
| ③ 결론 | 차이 없음 | 차이 없음 | **차이 없음** (2회차 동률) |

- **개선 1회** (`exp_plan_common`): 질문 만드는 방식을 "LLM이 다시 쓰기" → "원문 인용 + 코드 조립"으로 바꿈. 칸 정답률 0.333 → 0.893(기준 충족), 재현율 1항목 감소(경계에서 충족) → **채택**.

- 첫 측정의 실패: LLM이 다시 쓴 질문 9개 모두 표기 방침을 빠뜨리고 기획서 목표("인지도 확보")를 섞었다. 그래서 9개 모두 비슷한 사례 2개 미만이 되어 B 검색 범위가 한 번도 좁혀지지 않았다.

- 범위 좁히기(B)의 효과는 결론을 내리지 못했다. MRR은 3회 모두 B가 높았지만 미리 정한 결론 기준(Hit@3)은 바꾸지 않았다.

### 10-4. 남은 실패와 실제 기획서 시험

| 구분 | 관찰 |
|---|---|
| 항목 놓침 | 3회 모두 D3·E3("실제 촬영 + 일부만 AI") |
| 시기 흔들림 | 틀린 칸은 모두 시기. "2026년 4분기" → 반기 변환이 temperature 0에서도 실행마다 다름 |
| 실제 전시기획안 PDF(16쪽, 정성) | AI 항목 4개 모두 근거 부족 + "AI 사용 표기 방침, 집행 시기를 적어 주세요" 안내. 배경 설명(뮤직비디오 줄거리·그룹 소개) 2개를 제작 항목으로 잘못 고름, 업종 흔들림, 저작권 고지를 표기 방침으로 가져옴(원문 인용 검사로 빈 값 처리) |

**더미 0.89와 실제 문서의 차이가 크다.** 결과를 보고 프롬프트를 고치지 않고 사례로 기록했다. 개선 아이디어는 A·B·C 실패를 보고 떠올렸으므로, 판정은 새 더미 D·E·F로만 했고 A·B·C 재측정값(칸 0.861)은 '오염된 참고값'으로만 둔다. 가상 소비자 한마디·이유 피드백은 정량 측정 없이 정성 확인만 했다.

### 10-5. 화면 "기획서 확인" 탭

| 기능 | 내용 | 파일 |
|---|---|---|
| 입력 | 붙여 넣기 또는 파일 올리기(PDF·Word·HWPX). 메모리에서만 읽고 저장·임베딩하지 않음. 구형 .hwp는 PDF·HWPX로 저장하도록 안내 | `app/file_text.py` |

- 코드 검사: 근거 번호가 없거나 없는 번호를 쓴 문장, 숫자나 등급 단어(관찰됨·예상·가능성 등)를 쓴 문장은 지우고 "검사 기록"에 남긴다. 근거 부족이면 LLM을 부르지 않는다.
